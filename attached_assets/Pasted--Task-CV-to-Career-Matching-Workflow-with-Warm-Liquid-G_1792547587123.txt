# Task — CV-to-Career Matching Workflow with Warm Liquid Glass UI

## Project context

I am building FutureReady Workforce, an existing React + TypeScript + Vite frontend with an Express + TypeScript backend.

The application already has:
- A career-matching API implemented in Task #4.
- A JSON career dataset containing 15 role families, each with 30 listed skills and 227 distinct skill names overall.
- An existing dashboard with the "Roles that overlap with your skills" section.
- A Job Search feature with search filters, job details, and skill-overlap scoring.
- A warm orange-and-cream design system.
- Other dashboard sections, including Market Signals, the user's skills profile, and "A few skills to build."

I want to transform the existing career-matching section into a polished, interactive CV-to-career-matching experience.

**The central user journey should be:**

Upload CV → Extract skills → Animate and review detected skills → Calculate career matches → Explore relevant careers.

Do not create a new application or build a second career-matching engine. Extend the existing project.

---

## 1. Inspect the current implementation first

Before editing, inspect the current frontend, backend, career-matching API, dataset loader, skill-profile storage, generated API clients, Job Search integration, and existing CSS/theme conventions.

Some CV workflow code or UI may already exist. Reuse and improve it instead of duplicating routes, components, datasets, dependencies, or scoring logic.

Briefly identify the files you intend to change, then proceed with implementation. Keep changes focused on this feature and its necessary integration.

## 2. Replace the existing career-matching dashboard section

Replace the entire "Roles that overlap with your skills" dashboard card with the new three-step CV workflow.

Do not retain the old manual-matching panel beside the new workflow, since that would create two competing interfaces for the same feature.

The new section should contain three clearly numbered stages:

### Step 01 — Upload your CV

Provide a large, attractive drag-and-drop upload area with:
- A file upload icon.
- "Drop your CV here" heading.
- Support for PDF, DOCX, and TXT.
- A file-selection button.
- A short explanation that the CV will be analysed to identify skills and suggest matching careers.

Support file selection as well as drag-and-drop.

Show the uploaded filename, file size, and processing status when appropriate. Include a clear way to replace the selected CV or start again.

Do not display example skills or fabricated career scores as if a CV had already been analysed.

### Step 02 — Extract and review skills

After successful extraction, reveal the detected skills as interactive chips.

This is a key part of the user experience. The skills should appear dynamically, with each detected skill becoming visible through a subtle animation rather than appearing as an unexplained static list.

Use a brief staggered entrance animation, such as:
- A small upward movement.
- A gentle fade-in.
- A subtle scale from slightly smaller to normal size.
- A restrained orange accent or highlight as each chip appears.

The animation should feel polished and responsive, not like a flashy game or a loading animation that lasts unnecessarily long.

Use CSS animations or an animation library already present in the project. Do not add a heavy animation dependency just for this effect.

**Important animation rules:**
- Animate only skills that were actually detected.
- Do not hard-code the example chips from the design reference.
- Start the animation after extraction succeeds.
- Show a genuine loading or processing indicator while the backend is working.
- Avoid fake progress percentages or fabricated extraction results.
- Respect reduced-motion preferences and disable or simplify nonessential animations when requested by the user's device.
- Keep the interface usable while chips animate.

Each skill chip must be editable. Users must be able to remove an incorrectly detected skill, add a missing skill, and review the final list before matching.

Show a concise explanation that extraction can make mistakes and users should review their skills.

### Step 03 — Discover matching careers

After the user confirms the extracted skills, enable a clear primary action such as "Find matching careers."

Call the existing career-matching API with the reviewed skills.

Display actual results from the API, including:
- Ranked career families.
- Calculated skill-overlap percentages.
- Matched skills.
- Missing skills.

Show an attractive result card for each recommended career. Use a refined progress bar or similar visual indicator for the score.

The results must update when the confirmed skill list changes and the user runs matching again.

Do not show placeholder results, a fixed 60% score, or results from a previous CV while a new CV is being processed.

Explain that the score measures overlap with the dataset's listed skills. It is not the probability of getting hired.

Where relevant, let users continue to the existing Job Search feature with their confirmed skills.

## 3. Implement actual CV text extraction without an LLM

If the backend extraction logic does not already exist, implement it using compatible open-source Node.js libraries.

Possible choices include:
- `pdf-parse` or another compatible PDF text-extraction library for PDFs.
- `mammoth` for extracting raw text from DOCX files.
- Node.js text reading for TXT files.

Inspect the project's runtime and dependency setup before selecting and installing libraries.

Perform parsing and skill extraction on the backend. Do not rely exclusively on frontend processing.

For scanned or image-based PDFs, detect when ordinary PDF text extraction produces no useful text and show a clear message that OCR may be required. Do not claim successful extraction when the document could not be read.

Do not add an LLM, external AI API, paid inference service, RunPod, or model hosting for this task.

## 4. Extract skills using the existing dataset

Use the existing `career_roles_test.json` dataset and backend conventions.

Load the dataset through the existing data-loading mechanism. Do not create a second copy of its skill catalogue.

Identify skills in extracted CV text using deterministic, testable matching logic.

Requirements:
- Normalize letter casing and surrounding whitespace.
- Match complete skill names or phrases, not arbitrary substrings.
- Preserve meaningful punctuation in skills such as `node.js`, `react.js`, `next.js`, `ci/cd`, `c++`, and `c#`.
- Avoid false matches involving short skills such as `ai`, particularly when they occur inside another skill name such as `ai/ml`.
- Handle duplicate mentions without producing duplicate chips.
- Treat ambiguous, generic terms such as `data` and `software` carefully rather than assuming every occurrence proves a skill.
- Do not infer qualifications or skills that cannot be supported by the document and the extraction rules.
- Keep the detected-skill list and matching behaviour deterministic and testable.

The user must always be able to correct extraction mistakes before calculating career results.

## 5. Apply a warm Liquid Glass design

Use the attached Liquid Glass button reference as visual inspiration, while preserving FutureReady Workforce's existing orange-and-cream branding.

The result should resemble a modern, premium career-tech application rather than a blue or purple futuristic interface.

### Visual treatment

Use:
- Warm translucent cream and off-white surfaces.
- Subtle backdrop blur where appropriate.
- Fine semi-transparent borders.
- Gentle inner highlights and soft reflections.
- Restrained gradients.
- Soft, layered shadows.
- Smooth hover and pressed states.
- Existing orange accents for buttons, icons, selected skills, and progress indicators.

Prioritise the effect on the CV upload area, primary buttons, interactive skill chips, step indicators, and small overlays.

Keep longer text sections and most dashboard cards largely solid or only lightly translucent for readability.

Do not turn the entire application into transparent glass. Avoid neon glow, excessive gradients, heavy blur, exaggerated reflections, and large distracting animations.

Reuse existing theme variables and components wherever possible.

### Responsive layout and accessibility

- Keep the three stages visually organised with sufficient spacing.
- Ensure the section fits the existing dashboard without creating horizontal overflow.
- Adapt the layout for mobile screens.
- Maintain adequate contrast and visible keyboard focus indicators.
- Make upload, remove-skill, add-skill, confirm, and retry controls accessible.
- Provide sensible fallbacks where `backdrop-filter` is unsupported.
- Respect reduced-motion preferences.

## 6. Make the workflow a proper state machine

Handle the complete user journey explicitly.

**Initial state:** The upload area is ready. No extracted skills or matching results are displayed as if they were real.

**Uploading/processing state:** Show a genuine loading indicator, prevent duplicate submissions where appropriate, and display the selected filename.

**Extraction complete:** Animate the actual detected skill chips into view and allow users to edit them.

**Review state:** Enable the user to add, remove, and confirm skills. Do not calculate matches until the user explicitly proceeds.

**Matching state:** Call the existing API and show a loading state without displaying stale results as new ones.

**Results state:** Display the rankings, scores, matched skills, and missing skills returned by the backend.

**Error state:** Explain what failed, preserve the ability to retry when safe, and do not show fabricated results.

**Empty-skill state:** Explain that no recognised skills were found and offer manual skill entry or another file upload.

**Reset/replacement:** Allow the user to start over with another CV without accidentally mixing skills from the previous document.

Use the existing React state conventions and components where possible rather than creating unnecessary state-management infrastructure.

## 7. Integrate with the existing skills profile and Job Search

The confirmed CV skill list should be reusable by the existing career-matching and Job Search features, using the current profile-storage architecture where possible.

Users should not have to upload the same CV repeatedly to use the career and job-listing features within the same supported session.

Do not silently replace an existing profile before the user confirms the newly extracted skills.

Keep the existing Job Search implementation and its filters, detail pages, and provider architecture unchanged except where necessary to consume the confirmed skill list.

Do not introduce a new database or persist CV files or full extracted CV text just to support this workflow.

Ensure the dashboard's top-skill-overlap statistic reflects genuine confirmed matching data, or displays an appropriate empty state when no confirmed profile exists.

Keep Market Signals, the existing skills profile, and "A few skills to build" unless a small integration change is genuinely necessary.

## 8. Protect CV data

CVs may contain personal and contact information. Handle them conservatively.

- Validate file type, actual format where feasible, and size on the server.
- Apply a sensible upload limit, such as 5 MB.
- Reject malformed, unsupported, empty, and oversized files.
- Process uploads in memory where practical.
- If temporary storage is necessary, clean it up reliably.
- Do not log CV contents.
- Do not persist the uploaded CV or full extracted text in a database or permanent file store.
- Do not transmit CV contents to an external service.
- Return safe, understandable errors rather than stack traces or internal paths.
